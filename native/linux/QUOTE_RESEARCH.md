# Linux 引用消息适配进度

测试目标：Linux 微信 4.1.13.26，执行文件 SHA-256 与 `LINUX_WECHAT_SHA256` 一致。

- 收到受控私聊文字时，Linux 接收事件包含原消息编号，接收账号与登录账号一致。
- 对该文字在另一端使用微信原生“引用”，Linux 捕获到 type 49、appmsg type 57；安全解析器成功读取被引用的测试文字。
- 使用 `send_generic`、message type 49、subtype 57 和自行构造的 `refermsg` XML，接口回调成功，但对端看到的是普通文字。此方法未验证为原生引用发送，不能作为正式接口使用。
- Linux 的通用发送路径约 `0x6f7d903` 区分 message type 49 和 3；type 49 路径从正文读取 `type`，其后调用约 `0x6f834a0`。这些只是静态分析线索，不代表可直接调用或已确定对象布局。
- Windows 4.2.0.12 依赖原消息索引查询及原生引用对象构造；其地址、对象布局及调用约定不能直接用于 Linux。
- 实机在 Linux 微信界面引用文字并发送，接收方确认显示引用卡片。追踪命中 `0x738ff80`，该函数写入 type 49、subtype 57 并操作对象的 `0x190` 成员。一次采集的栈中有 `0x497315d`；静态分析显示 `0x49f3dc0` 可尾调用该函数并传入上下文中的引用对象。另有 `0x738fec0` 构造同类型对象，但该次捕获未命中它。上述线索尚未证明函数参数或对象的生命周期，不能直接接入发送。
- 静态扫描发现 `0x4a075cd` 调用 `0x738fec0`，调用方先检查第二个参数的 `0x350` 状态字节。另发现包含 `GetMessageListBySvrIds`、`GetMsgByServerIdList` 文本的若干查询路径；当前尚未证明它们与引用构造路径匹配，也未确认其参数与线程要求。
- `0x605e8a0` 从原生消息构造 0x350 字节 DTO：原对象 `+0x0c` 的类型复制到 DTO `+0x08`，会话字段 `+0x18`、账号字段 `+0x30` 分别复制到 DTO `+0x10`、`+0x28`；原对象 `+0xf8` 和 `+0x100` 分别复制到 DTO `+0x90` 和 `+0xa0`。
- 在 WSL 受控测试中，以接收桥获得的服务器消息编号、发送方和接收方共同对照，匹配到同会话 type 1 原生消息对象的 `+0xf8`。这是单次实测，不代表跨群、多账号或历史消息均已验证。
- 另一次 WSL 受控对照在 DTO 构造中观察到 `DTO+0x238` 的共享控制块非空，但其对象地址与上面的原生消息源对象不同；因此现有图片上下文持有逻辑不能直接视为原文字消息对象的生命周期保证。尚未确认该共享对象的类型和它与源对象的引用关系。
- `0x738fec0` 的四个参数被分别用于输出 shared 对象、引用来源描述、正文字符串和附加描述；它将类型/子类型组合写入生成对象 `+0xe4`，将引用来源描述复制到 `+0x190`。这些只是反汇编推断，引用来源的具体布局和释放规则仍未验证。
- `0x6197260` 检查来源 DTO 包装的 `+0x350` 有效标志后调用 `0x60f4b30` 生成较小描述；后者将 DTO `+0xa0` 复制到描述 `+0x20`。在上述实测中事件编号与来源 `+0xf8`（DTO `+0x90`）匹配，因此不能仅凭该拷贝假设描述 `+0x20` 就是事件编号；需核对两个字段的语义及构造后引用内容。

实机硬件断点确认了普通文字正文位于 DTO `+0xb8`，并观察到 `0x472e700` 完成独立副本构造。引用构造器把完整 DTO 拷到输出对象 `+0x1d8`，原消息编号在输出对象 `+0x268`，可用标志在 `+0x528`。在释放输入副本后，原生对象仍可提交。正式桥接重启后，Linux 微信停在文件传输助手时也能引用新收到的私聊。接收方确认了原生卡片及引用正文，点击卡片可定位到刚收到的原消息。

插件调用 `ctx.reply_quote(message, text)`。当前开放机器人启动后收到的普通私聊文字，按私聊会话和 64 位服务器消息编号在当前作用域的最近 16 份副本中查找。作用域清除和副本淘汰时调用原生析构函数 `0x472f190`。发送前重新核对账号、作用域代次及构造后对象的编号。引用群消息或查询旧历史记录仍需各自验证。
