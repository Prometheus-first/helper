# Linux 好友与群管理：当前研究记录

目标为项目固定指纹的官方 Linux 微信 4.1.13.26 x86_64。下述位置来自静态反汇编，只是研究线索，不是已验证接口，不得直接对真实账号调用。

| 请求 | CGI 字符串 | 静态调用链候选 |
| --- | --- | --- |
| 验证好友 | `/cgi-bin/micromsg-bin/verifyuser` | `0x76be360` → `0x69200e0` → `0x6920ca0` |
| 建群 | `/cgi-bin/micromsg-bin/createchatroom` | `0x76b7ff0` → `0x78c0310` → `0x78c2200` |
| 添加群成员 | `/cgi-bin/micromsg-bin/addchatroommember` | `0x76b9230` → `0x78be100` → `0x78bec30` |
| 邀请群成员 | `/cgi-bin/micromsg-bin/invitechatroommember` | `0x76b99b0` → `0x78c7050` → `0x78c8210` |

静态交叉引用只确认函数之间的直接调用和请求字符串；调用约定、结构、好友验证票据、添加与邀请的实际选择、服务端回执与线程生命周期均未确认。没有真实好友申请或获授权的群成员交互样本，不能开放自动通过、建群或邀请的后端能力。

原生消息通道已按合成样例增加 type 37 的有界接收，账号连接内存中的好友申请目录复用现有 XML 校验和去重逻辑。验证票据不会进入公开消息元数据或日志；该接收路径尚未用 Linux 微信的真实好友申请核对，因此暂不声明 `friend.request.receive`；自动通过也缺 `friend.request.accept`，插件保持不可用。

下一步：在获得独立测试申请及经同意的测试联系人后，对照实际消息与微信自身调用采样，先核对账户、参数及服务端回执，再做受限的真实测试。不要通过生产业务路径暴露未验证偏移，也不要把真实账号、票据或群标识记录在仓库中。

## 按 wxid 主动申请：离线对照

Windows 4.2.0.12 已验证的是来自共同群聊的申请：需个人 wxid、群 ID 和验证消息，Windows 原生调用中的 opcode 为 2、scene 为 14；这不能证明 Linux 的对象结构、调用约定或入口相同，也不能证明可以添加任意来源的陌生账号。

Linux 4.1.13.26 的已安装 ELF 指纹为 `2749535f299ba67feb8ef80cab898bb0531fa8f376b16f8a72db706811c84132`。离线反汇编显示候选 `0x76be360` 从调用参数对象读取 `+0x10` 和 `+0x28` 后调用 `0x69200e0`，但这些字段的语义、实际业务来源和结果类型尚未验证；不能据此构造请求或开启 `friend.request.send` 能力。需后续对微信自己发起的共同群好友申请采集调用对象，确认群来源、目标、验证消息、线程、生命周期和结果，再编写原生实现及实测。

本次只做静态分析，不触发好友申请。当前 REA 服务运行在 Windows，深度 Ghidra 提供方不支持 Linux ELF；上述汇编观察来自 WSL 内只读 objdump，不是运行时验证。
